# 登录、任务与部署恢复

先确认问题属于进程、持久化、上游账号、单个任务还是下载。保留原请求 ID 与资源 ID，再选择下面的操作。不要因一句“连不上”直接重新生成或重置所有配置。

## 状态分别代表什么

| 证据 | 可以说明 | 不能单独说明 |
| --- | --- | --- |
| `/health` 返回 200 | 当前业务进程可访问 | Muse 登录或推理可用 |
| `/admin/status` ready | 本进程已加载或验证过会话资料 | 此刻上游会话仍有效、一定能生成媒体 |
| persisted | 加密保存路径已建立 | 重启后已恢复、真实请求已成功 |
| 重启恢复成功 | 同数据目录和密钥可解密加载 | 上游会话未被撤销 |
| 一个真实文字请求完成 | 该时刻文字链路成功 | 图片、视频或所有输入方式都通过 |
| 媒体文件下载并解码 | 该资源已实际取回 | 提示词全部细节和音色一致性通过 |

## 上游会话过期

在没有在途文字或媒体创作时，到官方网页正常重新登录本人账号。服务器使用者先恢复 SSH-L 到管理端口，再生成新的单次授权码，通过扩展明确授权。不要把会话发到工单、聊天或 GitHub，也不要导出整个浏览器 Profile。

新授权沿用本实例业务地址与配置。若换了 Muse 账号，先保存旧作品，确认没有未完成任务；服务忙碌时应拒绝覆盖会话。

## 加密存储或配置错误

进程启动失败且提示密钥／密文无效时，先核对数据目录和原来的 `MUSE2API_SESSION_KEY`。不要生成一份新密钥覆盖旧 `.env` 来“修复”；这会使旧会话无法解密。

如果原密钥确实丢失，只能按正常流程重新授权；保留旧密文与任务状态供自己审计，不要上传。不同机器可迁移本项目 AES-GCM 状态，但必须同时、安全地迁移正确密钥并重设文件权限，不能将密文当作无敏感内容公开分发。

业务 API Key 参与资源归属。轮换它前先下载重要资源，保留旧配置的安全备份；不要假定换 Key 后所有旧媒体仍能被新 Key 查询。不要通过伪造 `X-Muse-Owner` 绕过归属。

## 图片／视频状态未知

`unknown`、超时、断线或 5xx 表示客户端不能确定交付；`failed` 也不会让客户端自动再次 POST。恢复顺序：

1. 阅读原本地回执，确认原 request-id、Base URL、资源 ID。
2. 有资源 ID 时只查询它。已完成则下载它；只下载失败时只恢复 GET。
3. 没有资源 ID 时，将不含 Key 的请求 ID、时间和固定错误分类交给实例维护者定位；不要换编号或删回执绕过拦截。
4. 服务重启把未完成任务转为 `unknown`，不会自动重放。原 SDK 没有通过本版 HTTP 暴露原生 SID／ACK 恢复合同，因此网站原生历史检查与本项目资源状态是不同证据。

本版不提供取消或删除视频的 HTTP 端点。不要调用未实现的路径后将 404 解释为“上游任务已取消”。

## 升级与回退

升级前保存当前源码 commit／镜像摘要、私密环境文件与持久目录的受限备份。会话密文和解密密钥都不进入 Git 或公开发布包。备份本身同样按私密材料处理。

确认无在途创作后，再停止自己的实例、替换二进制或镜像，保留原私密配置与数据目录。回退使用上一个已验证的二进制或镜像，不更换密钥、不清空任务、不删除 volume。

回退后依次检查进程、加密状态恢复、模型列表和一条明确授权的实际文字请求；需要媒体时单独创建一次新验收作品。旧任务只查原 ID。对日志进行必要脱敏后再报告问题，不上传 `.env`、会话、运行目录、浏览器截图或完整请求头。
